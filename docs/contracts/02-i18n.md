# Vertrag 1b — Mehrsprachigkeit

**Status:** verbindlich ab Stufe 1
**Sprachen:** Deutsch (Vorlage) und Englisch, ab der ersten Zeile

## Ausgangslage

Die PWA hält in `js/core/i18n.js` **1.260 Schlüssel** in 25 Namespaces — und Deutsch und
Englisch sind in **exakter Parität**. Ein Schlüsselpfad-Diff ergibt in beide Richtungen die
leere Menge. Für alles, was Funktionen der PWA entspricht, ist Englisch damit Migration statt
Übersetzungsarbeit.

Die Übungsinhalte sind anders aufgebaut: In `data/exercises_*.json` ist **Englisch die Basis**
und Deutsch das Overlay unter `i18n.de` mit drei Feldern (Anleitung, Cues, Fehler). Der
deutsche Name liegt separat unter `name_de` — und fehlt bei 24 der 100 kuratierten Übungen.

## Stack

`flutter_localizations` + `intl` + das eingebaute `flutter gen-l10n`. **Kein `build_runner`.**

Erwogen und verworfen: `slang` passt mechanisch besser (verschachtelte Namespaces,
`{}`-Interpolation). Trotzdem ARB, weil `flutter_localizations` für `MaterialLocalizations`
ohnehin gebraucht wird — heute sprechen unsere Bottom Sheets, Dialoge und
Textfeld-Kontextmenüs Englisch in einer deutschen App —, weil ICU-Plurale nativ sind, und
weil ausgerechnet die App-weiteste Querschnittsaufgabe keine Fremdabhängigkeit tragen sollte.

```yaml
# l10n.yaml
arb-dir: lib/l10n/arb
template-arb-file: app_de.arb
output-dir: lib/l10n/gen
output-localization-file: app_l10n.dart
output-class: AppL10n
nullable-getter: false
untranslated-messages-file: l10n/untranslated.json
use-escaping: true
```

Kein `synthetic-package` — der Schalter ist abgeschafft. Die erzeugten Dateien werden
**eingecheckt**, damit die CI per `git diff --exit-code` erzwingen kann, dass sie aktuell sind.

## Vorlagensprache ist Deutsch

Der Autor schreibt Deutsch. Damit meldet `untranslated.json` fehlendes **Englisch** — also
genau die Richtung, die in der Praxis wegdriftet.

## Schlüsselkonvention

Voller Punktpfad in lowerCamelCase: `plan.meta.exercises` → `planMetaExercises`.

Auf den echten Daten geprüft: 1.260 Schlüssel, **null Kollisionen**, längster Schlüssel
51 Zeichen. Der Namespace bleibt als Präfix lesbar — `l10n.workoutScreenExerciseOf(1, 3)`.

Verworfen: Aufteilung in mehrere ARB-Sätze pro Namespace. Das dreifacht die Build-Verdrahtung
und kauft dafür nur Gruppierung in der Autovervollständigung.

## Platzhalter

JS `{name}` **ist** ICU `{name}` — die Interpolation portiert unverändert. Der einzige
nichttriviale Schritt sind die Typangaben, weil `gen-l10n` sonst auf `Object` fällt und
`toString()` aufruft, was lokalisierte Ziffern verliert:

```json
"workoutScreenExerciseOf": "Übung {current} von {total}",
"@workoutScreenExerciseOf": {
  "placeholders": {
    "current": { "type": "int" },
    "total":   { "type": "int" }
  }
}
```

Von 1.260 Schlüsseln interpolieren **92**; **51** tragen eine Zahl.

## Plurale

Die PWA hat **keine** Pluralbehandlung. `{count} Sessions` ist bei n=1 in beiden Sprachen
falsch. Das wird bei der Migration repariert, nicht mitgeschleppt.

Von den 51 numerischen Schlüsseln sind rund **20 echte Pluralkandidaten**. Das
Migrationsskript rät **nicht** — es schreibt den flachen String und legt
`l10n/plural_candidates.md` als Arbeitsliste an. Ein Durchgang von Hand, eine Sitzung.

```json
"planMetaExercises": "{count, plural, =0{Keine Übungen} one{{count} Übung} other{{count} Übungen}}"
```

Deutsch und Englisch nutzen beide nur `one` und `other`, die ARB-Dateien bleiben also
strukturgleich. Das handgebaute Paar `supersetBannerOne` / `supersetBannerOther` verschmilzt
zu einem Schlüssel, und die aufrufende Stelle verliert ihr `if`.

## Zahlen, Datum, Einheiten

**Alles läuft über eine Fassade.** Kein direkter `intl`-Aufruf in Widgets.

```dart
// lib/core/i18n/atem_format.dart
class AtemFormat {
  static AtemFormat of(BuildContext c);

  String weightKg(double kg);      // lokalisiertes Dezimaltrennzeichen
  String clock(Duration d);        // mm:ss, sprachunabhängig
  String weekdayShort(DateTime d); // MO/DI vs MO/TU
  String dateShort(DateTime d);
  String monthYear(DateTime d);
  double? parseNumber(String s);   // Eingabe zurück in eine Zahl
}
```

Das behebt vier Fehler auf einmal:

1. `formatDateTimeText()` und `formatDateShortText()` in der PWA sind fest auf `de-DE`
   verdrahtet, unabhängig von der Spracheinstellung
2. Es gibt nirgends `Intl.NumberFormat` — Dezimaltrennzeichen werden nicht lokalisiert
3. `_PerformancePainter` hält `['MO','DI','MI',…]` fest verdrahtet — Übersetzungsfehler und
   Wochenanfang-Annahme in einem
4. `WorkoutSet.weightValue` behilft sich mit `weight.replaceAll(',', '.')`

Einheiten (kg/lbs, cm/inch) folgen der **Profileinstellung**, nicht der Sprache. Ein
Deutscher in England will weiter Kilogramm sehen.

## Keine Textliterale in Widgets

Ein `SimpleStringLiteral` als erstes Argument von `Text(…)`, als `TextSpan(text:)` oder als
`Semantics(label:)` ist verboten und wird vom Analyzer gemeldet. Das gilt auch für englische
Literale — sonst wandert Text am ARB vorbei ein und fällt erst beim Sprachwechsel auf.

## Keine UI-Texte in der Domäne

`ReadinessLevel` und `SetType` tragen heute deutsche Strings **und** `Color`-Werte als
Enum-Konstanten. Beide Dateien importieren `package:flutter/widgets.dart` allein deshalb.

Auflösung in drei Schritten:

1. Enums werden reine Daten, ohne Flutter-Import — nur Werte und `fromScore` bzw. `next`
2. Darstellung als Extension in `presentation/`:
   ```dart
   extension ReadinessLevelUi on ReadinessLevel {
     Color get color => switch (this) { … };
     String label(AppL10n l) => switch (this) { … };
   }
   ```
   Ein erschöpfendes `switch` über ein Enum ist ein Compile-Fehler, sobald ein Fall fehlt.
   Eine neue Stufe **erzwingt** damit Farbe und Text — kostenlose Absicherung.
3. `atem_no_flutter_import_in_domain` verhindert den Rückfall

Nebenbefund: `SetType.label` ist nicht sprachneutral. `'W'` für Warmup funktioniert im
Deutschen nur zufällig — „Aufwärmsatz" wäre `'A'`. Genau so etwas versteckt eine
Enum-Konstante. Es wird `l10n.setTypeShortWarmup`.

## Migrationsumfang

**Nicht alle 1.260 Schlüssel.** Bei zwei Screens wären tausend ungenutzte Getter Verfallsmasse
und würden die Meldung fehlender Übersetzungen zumüllen.

Für das Fundament: `common, nav, format, errors, dashboard, workout` — rund **242 Schlüssel**.
Der Rest kommt mit seinem Screen aus dem eingecheckten Vorrat.

## Migrationsweg

Zwei kleine Skripte, kein cleveres.

**`tool/i18n/extract.mjs`** — die JS-Datei hat kein `module.exports` und endet in
`window.t = t`. Nicht mit Regex durch 3.200 Zeilen verschachtelter Literale, sondern
auswerten:

```js
const tr = vm.runInNewContext(src + '\n;translations',
  {window: {}, Intl, Date, Number, String, Math});
```

Ergibt `tool/i18n/legacy_de.json` und `legacy_en.json` — eingecheckt als Vorrat, nicht
kompiliert.

**`tool/i18n/to_arb.dart`** — flach klopfen, camelCase, Typangaben ableiten. Das Skript
**prüft zusätzlich**, dass keine camelCase-Kollision entsteht und die Schlüsselmengen beider
Sprachen gleich sind. Beides gilt heute; ein späterer Lauf ist damit sicher statt still
verlustbehaftet.

## Board-Schlüssel und ARB-Schlüssel

Seit dem Handoff vom 28.08.2026 sind die Stringtabellen der Design-Boards die
Quelle. Sie benennen ihre Schlüssel als **Punktpfad** (`exercise.field.name`).

Flutter erzeugt aus jedem ARB-Schlüssel einen Dart-Getter; ein Punkt darin ist
kein gültiger Bezeichner. Die Abbildung ist deshalb festgelegt und umkehrbar:

    exercise.field.name   →   exerciseFieldName
    delete.step2.noUndo   →   deleteStep2NoUndo

Der Punktpfad bleibt die **Identität** des Strings und steht unverändert in der
`description` des ARB-Eintrags. Damit lässt sich jederzeit gegen das Board
prüfen — `tool/board_strings.py` tut genau das.

### Platzhalter heissen in beiden Sprachen gleich

Die Boards benennen sie sprachlich: Deutsch `{alt}`/`{neu}`, Englisch
`{old}`/`{new}`. Für Flutter sind Platzhalter aber Bezeichner, keine Wörter —
unterschiedliche Namen erzeugen Methoden mit unterschiedlichen Parametern, und
`new` ist obendrein ein Dart-Schlüsselwort.

Deutsch ist die Vorlagensprache und gewinnt. `tool/board_strings.py` gleicht
die englische Fassung beim Übertragen nach Position an. Betroffen waren fünf
Strings aus Modul 7 und 8.
